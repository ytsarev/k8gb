# ContribFest Exercise: Fixing Dependency Update Breaking Changes

Related PR: https://github.com/k8gb-io/k8gb/pull/2041

## Overview

This exercise demonstrates how to fix compilation errors that occur when updating Kubernetes dependencies, specifically when a dependency adds new methods to an interface that mocked implementations must support.

**Time Required:** 15-30 minutes

**Skills Learned:**
- Understanding Go interfaces and mocks
- Working with Kubernetes controller-runtime
- Using MockGen for generating test mocks
- Debugging compilation errors after dependency updates

## Background

K8GB uses [controller-runtime](https://github.com/kubernetes-sigs/controller-runtime) from the Kubernetes project. When this library is updated, interfaces may change by adding new methods. Since our test code uses mocked implementations of these interfaces (generated by [MockGen](https://github.com/uber-go/mock)), we need to regenerate the mocks to include the new methods.

## The Problem

### Scenario

Renovate bot automatically created a PR to update `sigs.k8s.io/controller-runtime` from v0.21.0 to v0.22.4:

**Commit:** `f4946403ba0eec2e066b9ebc6cc6bf5ebcc01f5d`

This update introduced a breaking change:
- The `client.Client` interface gained a new `Apply` method
- Our mock implementation (`MockClient`) didn't have this method
- Tests failed to compile with the error:

```
controllers/gslb_controller_reconciliation_test.go:110:16:
cannot use cl (variable of type *mocks.MockClient) as client.Client value in struct literal:
*mocks.MockClient does not implement client.Client (missing method Apply)

controllers/handlers_test.go:219:49:
cannot use client (variable of type *mocks.MockClient) as client.Client value in argument to NewIngressHandler:
*mocks.MockClient does not implement client.Client (missing method Apply)
```

### Understanding the Error

When Go tells you that a type "does not implement" an interface, it means:
1. The interface defines certain methods
2. Your type is missing one or more of those methods
3. You cannot use your type where the interface is expected

In this case:
- `client.Client` is an interface (from controller-runtime)
- `*mocks.MockClient` is a mock implementation of that interface
- The interface was updated to require an `Apply` method
- Our mock doesn't have that method yet

## The Solution

The fix is straightforward: regenerate the mocks to include all current interface methods.

### Step 1: Check the Current State

First, let's examine what methods our mock currently has:

```bash
gh pr checkout 2041
```

```bash
grep '^func (m \*MockClient)' controllers/mocks/client_mock.go
```

You'll notice there's no `Apply` method in the output.

### Step 2: Understand How Mocks Are Generated

Look at the `Makefile` to see how mocks are created:

```bash
grep -A 10 'mocks:' Makefile
```

You'll see commands like:
```makefile
mockgen -package=mocks -destination=controllers/mocks/client_mock.go \
    sigs.k8s.io/controller-runtime/pkg/client Client
```

This tells MockGen to:
- Generate mocks for the `Client` interface
- From the package `sigs.k8s.io/controller-runtime/pkg/client`
- Put them in `controllers/mocks/client_mock.go`

### Step 3: Regenerate the Mocks

Run the make target that regenerates all mocks:

```bash
make mocks
```

This will:
1. Install the correct version of MockGen
2. Regenerate all mock files
3. Inject license headers into the generated files

### Step 4: Verify the Fix

Check that the `Apply` method now exists:

```bash
grep '^func (m \*MockClient) Apply' controllers/mocks/client_mock.go
```

You should see output like:
```go
func (m *MockClient) Apply(arg0 context.Context, arg1 runtime.ApplyConfiguration, arg2 ...client.ApplyOption) error {
```

### Step 5: Run the Tests

Verify that the tests now compile and pass:

```bash
make test
```

**WAIT!** You might encounter another error...

## Additional Issue: Go 1.25 covdata Bug

### The Second Problem

After regenerating the mocks, you might see this error when running tests:

```
Running the unit tests
env -u LOG_FORMAT -u LOG_LEVEL -u EXT_GSLB_CLUSTERS_GEO_TAGS -u EDGE_DNS_SERVER go test ./... -coverprofile cover.out
# github.com/k8gb-io/k8gb/api/v1beta1
go: no such tool "covdata"
# github.com/k8gb-io/k8gb
go: no such tool "covdata"
ok  	github.com/k8gb-io/k8gb/controllers	0.568s	coverage: 32.3% of statements
...
make: *** [Makefile:512: test] Error 1
```

The tests pass but `make test` exits with error code 1! This is a known bug in Go 1.25's toolchain auto-switching mechanism.

### Understanding the covdata Issue

- The `covdata` tool is used internally by Go for coverage data processing
- In Go 1.25.x, there's a bug where the toolchain auto-switching mechanism fails to find the `covdata` tool
- This happens specifically for packages without test files when running with `-coverprofile`
- The tests themselves pass, but the coverage processing fails

### The Fix

According to [this Stack Overflow discussion](https://stackoverflow.com/questions/79780882/go-no-such-tool-covdata-in-go-1-25), there are two approaches:

**Option 1: Set GOTOOLCHAIN environment variable (RECOMMENDED)**

Update the Makefile to set `GOTOOLCHAIN=go1.25.2+auto`:

```makefile
# run tests
.PHONY: test
test:
	$(call generate)
	$(call crd-manifest)
	@echo -e "\n$(YELLOW)Running the unit tests$(NC)"
	env -u LOG_FORMAT -u LOG_LEVEL -u EXT_GSLB_CLUSTERS_GEO_TAGS -u EDGE_DNS_SERVER GOTOOLCHAIN=go1.25.2+auto go test ./... -coverprofile cover.out
```

The `+auto` suffix tells Go to use the specified toolchain as a baseline while still allowing version switching based on project requirements.

**Option 2: Add toolchain directive to go.mod**

Add this line to your `go.mod` file after the `go` directive:

```go
go 1.25.3

toolchain go1.25.3
```

**Note:** This approach has limitations:
- `go mod tidy` may remove the directive if it matches your current Go version
- It may still produce the covdata error in some cases
- The environment variable approach is more reliable

### Verify the Complete Fix

Now run the tests again:

```bash
make test
```

This time, you should see:
- ✅ No compilation errors
- ✅ No "covdata" errors
- ✅ All tests pass
- ✅ Exit code 0

```bash
echo $?  # Should output: 0
```

Success! All tests should pass successfully!

## Key Takeaways

1. **Interface Changes:** When dependencies update interfaces, implementing types must be updated to match

2. **Generated Code:** Mocks are generated code - they should be regenerated when interfaces change

3. **Makefile Targets:** Projects often have make targets (`make mocks`) for regenerating code

4. **Test Failures:** Compilation errors in tests often indicate mocks are out of sync

5. **Toolchain Bugs:** Be aware of Go version-specific issues like the 1.25 covdata bug

6. **Environment Variables:** Sometimes environment variables like `GOTOOLCHAIN` provide better workarounds than code changes

7. **CI/CD:** Automated checks can prevent out-of-sync generated code from being merged

## Troubleshooting

### "mockgen: command not found"

The `make mocks` target installs mockgen automatically. If you see this error:
```bash
go install go.uber.org/mock/mockgen@v0.4.0
```

### "import cycle not allowed"

This usually means you're trying to mock an interface in the same package. Use `mockgen -source` instead:
```bash
mockgen -source=myfile.go -destination=mocks/myfile_mock.go
```

### "go: no such tool 'covdata'" error

If you see this error when running tests with Go 1.25.x:

1. **Quick fix:** Set the GOTOOLCHAIN environment variable in your Makefile:
   ```makefile
   env GOTOOLCHAIN=go1.25.2+auto go test ./... -coverprofile cover.out
   ```

2. **Alternative:** Add `toolchain go1.25.3` to your go.mod (though this may be removed by `go mod tidy`)

3. **Verify the fix:**
   ```bash
   make test
   echo $?  # Should be 0
   ```

See the "Additional Issue: Go 1.25 covdata Bug" section above for detailed explanation.

### Tests still fail after regenerating mocks

1. Check that you're running tests with the latest mocks:
   ```bash
   go clean -testcache
   make test
   ```

2. Verify the mock file has the new method:
   ```bash
   grep 'Apply' controllers/mocks/client_mock.go
   ```

3. Check if there are other interface changes you missed:
   ```bash
   go build ./...
   ```

## Follow-Up Contribution Ideas

After completing this exercise, here are some ways you can contribute to K8GB:

### 1. Add CI Check for Mock Synchronization

**Problem:** Out-of-sync mocks can slip into PRs if contributors forget to run `make mocks`.

**Solution:** Add a GitHub Actions workflow to verify mocks are up-to-date:

```yaml
# .github/workflows/verify-mocks.yaml
name: Verify Mocks
on: [pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - name: Generate mocks
        run: make mocks
      - name: Check for differences
        run: |
          git diff --exit-code controllers/mocks/ || \
            (echo "Mocks are out of sync. Run 'make mocks' locally." && exit 1)
```

This catches the problem before it gets merged!

### 2. Automate GOTOOLCHAIN Updates with Renovate

**Problem:** When Renovate updates the Go version in `go.mod`, the `GOTOOLCHAIN` environment variable in the Makefile can become outdated.

Example:
- Renovate updates: `go 1.25.2` → `go 1.25.3`
- Makefile still has: `GOTOOLCHAIN=go1.25.2+auto`
- Result: Mismatched toolchain versions

**Solution:** Configure Renovate to update both files together using `regexManagers`.

Add this to your `.github/renovate.json` or `renovate.json`:

```json
{
  "extends": ["config:base"],
  "regexManagers": [
    {
      "fileMatch": ["^Makefile$"],
      "matchStrings": [
        "GOTOOLCHAIN=go(?<currentValue>\\d+\\.\\d+\\.\\d+)\\+auto"
      ],
      "depNameTemplate": "go",
      "datasourceTemplate": "golang-version",
      "versioningTemplate": "loose"
    }
  ]
}
```

**How it works:**
- `fileMatch`: Tells Renovate to scan the Makefile
- `matchStrings`: Regex to find and extract the version from `GOTOOLCHAIN=go1.25.2+auto`
- `datasourceTemplate`: Uses Go version datasource to check for updates
- When Renovate updates `go.mod`, it also updates the Makefile in the same PR

**Bonus:** You can test this locally if you have Renovate CLI:
```bash
npm install -g renovate
renovate --dry-run --require-config=ignored
```
